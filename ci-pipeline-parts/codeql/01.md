## 2. Your CodeQL workflow  
**For your Java/Spring Boot application:**
```yaml
name: CodeQL

on:
  pull_request:
    branches:
      - main

  push:
    branches:
      - main

  schedule:
    - cron: '30 2 * * 1'

permissions:
  contents: read
  security-events: write
  actions: read

jobs:

  codeql:
    name: CodeQL
    runs-on: ubuntu-latest

    steps:

      # -----------------------------------------
      # 1. Checkout
      # -----------------------------------------
      - name: Checkout
        uses: actions/checkout@v4

      # -----------------------------------------
      # 2. Setup Java
      # -----------------------------------------
      - name: Setup Java 17
        uses: actions/setup-java@v4
        with:
          java-version: '17'
          distribution: temurin
          cache: maven

      # -----------------------------------------
      # 3. Initialize CodeQL
      # -----------------------------------------
      - name: Initialize CodeQL
        uses: github/codeql-action/init@v3
        with:
          languages: java
          queries: security-extended

      # -----------------------------------------
      # 4. Build
      # -----------------------------------------
      - name: Build
        run: mvn clean package -DskipTests

      # -----------------------------------------
      # 5. CodeQL analysis
      # -----------------------------------------
      - name: Analyze
        uses: github/codeql-action/analyze@v3
        with:
          category: "/language:java"
```

## 3. What happens when the PR is created?  
Suppose you create:  
```text
PR #123

feature/payment-api
        ↓
       main
```
Because we have:  
```yaml
Because we have:
```
CodeQL runs against the PR. GitHub supports CodeQL analysis on pull requests and reports the results as a code-scanning check.  

Imagine CodeQL finds:   

```text
SQL Injection          HIGH
XSS                    MEDIUM
Weak cryptography      LOW
```
The PR will show the Code scanning results check.  

GitHub's documentation specifically says that new alerts in the PR can appear as annotations, and the code-scanning check contains the results.  

## 4. Now comes the important part: Ruleset  
```text
GitHub Repository
        ↓
Settings
        ↓
Rules
        ↓
Rulesets
        ↓
New ruleset
        ↓
New branch ruleset
```
GitHub's current documentation uses this path for configuring code-scanning merge protection.  

## 5. Create your ruleset  
Give it a name such as:  
```text
Production Branch Security Protection
```
Set:  
```text
Enforcement status:
Active
```
Target branch:  
```text
main
```
Conceptually:  
```text
Ruleset
│
├── Name
│     └── Production Branch Security Protection
│
├── Enforcement
│     └── Active
│
└── Target branches
      └── main
```
